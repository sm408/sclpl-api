01 — POSITION

What sclpl is

Programmable API workflows, written as files and run locally. sclpl reads a workflow, infers the dependency graph from @references, runs each step the moment its inputs are ready, and writes CSV, JSON, NDJSON, Parquet, Excel, or SQLite. No server, no accounts, no web UI — just workflow files, typed Python values, and output files you own.

The problem it targets: most API jobs start as one request and end as a brittle one-off script. sclpl gives that middle ground a shape — pagination, validation, joins with local data, transforms, run history, and export — without turning every job into a bespoke Python program.

02 — WHAT SHIPS TODAY

Ten things it already does

01

Continuous scheduler

Writing @accounts inside a step is what makes it wait for accounts — there's no separate needs: list to maintain. A step starts the instant its own references land, so independent branches overlap automatically.

02

Built-in pagination

Cursor, token, offset, and Link:-header pagination are one line (paginate cursor cursor_path=... param=... max_pages=...) — the usual first thing hand-rolled scripts get wrong.

03

Data workbench

Flatten nested JSON, explode arrays into rows, join records against local sources (including SQLite), group/aggregate, profile a table, and export to CSV, JSON, NDJSON, Parquet, Excel, or SQLite.

04

Assertions with distinct exit codes

assert_rowcount, assert_schema, assert_unique, and assert_no_nulls fail with exit code 4, not 1 — automation can tell "the API failed" apart from "the data was wrong."

05

Secrets that refuse to be sloppy

Credentials go to the OS keyring (sclpl[keyring]) or an encrypted file (sclpl[crypto]). If neither safe backend is installed, secret storage fails loudly instead of falling back to plaintext.

06

Operational memory

Every run keeps local history: sclpl runs list, show, search, diff, replay, export, pin, prune — an overnight job stays inspectable the next morning.

07

Modes and limits

@mode partial / full / smoke run a subset of a workflow for a fast local check; @limits concurrency=8 host_concurrency=4 timeout=20 caps how hard a run leans on a target API.

08

Escape hatches, not lock-in

Register a SHA-256-pinned Python script and call it with sclpl python NAME — no plugin packaging required. Need something reusable? Scaffold a plugin against the public sclpl.ext.api, the same surface the bundled plugins use.

09

Editor support, stays in sync

sclpll-extras carries the VS Code extension, the SCLPLL language server, an Azure Blob plugin, and a workflow library — all built on the installed sclpl package, so syntax can't drift between CLI and editor.

10

Degrades on purpose under load

When memory pressure rises on a large run, intermediates spill to disk and concurrency backs off before the OS has to intervene — documented behavior, not a crash waiting to happen.

03 — WHY NOT JUST SCRIPT IT

Same workflow, three ways

Fetch two independent resources, join them, publish a report — in hand-written Python, a YAML automation file, and .sclpll.

python — asyncio~30 lines
import asyncio, aiohttp, os

TOKEN = os.environ["API_TOKEN"]  # secrets: your job
HEADERS = {"Authorization": f"Bearer {TOKEN}"}

async def fetch(session, path):
    for attempt in range(3):
        async with session.get(path, headers=HEADERS) as r:
            if r.status < 500:
                r.raise_for_status()
                return await r.json()
    raise RuntimeError("retries exhausted")

def join(accounts, prices):
    by_id = {p["account_id"]: p for p in prices}
    return [{**a, **by_id.get(a["account_id"], {})}
            for a in accounts]

async def run():
    async with aiohttp.ClientSession(BASE) as s:
        # you write the parallelism yourself
        accounts, prices = await asyncio.gather(
            fetch(s, "/accounts"),
            fetch(s, "/prices"),
        )
        merged = join(accounts, prices)
        async with s.post("/reports", headers=HEADERS,
                           json=merged) as r:
            r.raise_for_status()

asyncio.run(run())
Retry, join, and the parallel fetch are each hand-written — correct, but every one is a place to introduce a bug, and none of it is reusable in the next workflow.
yaml automation~24 lines + a script
steps:
  - id: accounts
    run: |
      curl -sf --retry 3 "$BASE/accounts" \
        -H "Authorization: Bearer $API_TOKEN" \
        > accounts.json

  - id: prices
    run: |
      curl -sf --retry 3 "$BASE/prices" \
        -H "Authorization: Bearer $API_TOKEN" \
        > prices.json

  - id: merged
    needs: [accounts, prices]
    # join isn't a shell primitive - out to a script
    run: python join.py accounts.json prices.json \
      > merged.json

  - id: publish
    needs: [merged]
    run: |
      curl -sf -X POST "$BASE/reports" \
        -H "Authorization: Bearer $API_TOKEN" \
        -d @merged.json
Reads clean until step 3 — real logic can't live in YAML, so it falls out into join.py. accounts/prices only run together if the runner honors needs: as a real DAG.
.sclpll~20 lines
@workflow account_price_report
  "Accounts + prices, merged and posted"

@var base = "https://api.example.com"
@var token = "{{secret('api_token')}}"

@step accounts
  get {{base}}/accounts
  header Authorization: Bearer {{token}}
  retry 3

@step prices
  get {{base}}/prices
  header Authorization: Bearer {{token}}
  retry 3

@step shaped_accounts
  flatten @accounts.body

@step shaped_prices
  flatten @prices.body

@step merged
  join @shaped_accounts @shaped_prices account_id how=left

@step publish
  post {{base}}/reports
  header Authorization: Bearer {{token}}
  body @merged
accounts and prices reference nothing but their own inputs, so the scheduler runs them together — no gather, no needs:. secret() reads the keyring/encrypted store by default.

On "speed": a carefully hand-tuned asyncio.gather script can run just as fast as sclpl for this exact shape — we don't have head-to-head runtime benchmarks yet. The honest version: a plain script or a linear YAML runner is only as parallel as the author remembered to make it; a .sclpll workflow is parallel by default because the scheduler reads it straight off the dependency graph.
