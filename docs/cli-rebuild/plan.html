01 — The thesis

One binary. Declarative pipelines. Nothing hidden behind a UI.

Today SCLPLAPI has three front ends fighting over one engine: a Textual TUI, a half-finished Vue studio, and a thin CLI. The engine underneath was shaped by the TUI’s needs — everything is a string, because a terminal widget only ever displays strings.

That single accommodation is what blocks every feature on your list. You cannot compare a > b, sum two fields, sort a result set, or hand a dataframe to the next step when the value model coerces everything to str on the way out of a step. So this is not a port of the CLI — it is a rebuild of the value model, the scheduler, and the transport, with the CLI as the only consumer.

The product becomes sclpl: a pipeline runner for HTTP APIs that takes a workflow by name or by path, resolves a dependency graph, runs it as fast as the remote will allow, and writes CSV, JSON, Parquet, or Excel out the other end — with progress you can actually watch.

Design rule that decides most arguments later: stdout is data, stderr is interface. Progress bars, spinners, and status lines go to stderr. Results go to stdout. sclpl orders --format json | jq works while the progress bar is still animating on your screen.
02 — Three users, one tool

Progressive disclosure, not three products

Every capability exists at three levels of power. The analyst uses the declarative form; the data engineer composes functions; the software engineer implements the primitives. Same concepts, same file format, same runtime — you only descend a level when you need to.

Tier 1 · Analyst

Writes JSON. Runs it.

Never opens Python. Never thinks about concurrency, sessions, or memory.

  • Declares endpoints, variables, and an output file
  • Uses built-in functions by name: flatten, save_csv, dedupe
  • Runs a colleague’s imported workflow by name, in partial mode, on their own file
  • Gets a live progress view and a readable failure
Tier 2 · Data engineer

Wires functions and plugins.

Composes the primitives, tunes throughput, installs connectors.

  • SCLPLL for terser authoring, or keeps JSON
  • Joins, merges, filters, pagination strategies
  • Defines the modes: which 12 of 20 steps run in partial
  • Installs plugins for databases, scrapers, warehouses
Tier 3 · Software engineer

Implements the primitives.

Writes typed, async, testable extensions that the other two tiers consume by name.

  • Registers function overloads for new types
  • Ships plugins with connectors, auth providers, DSL verbs
  • Adds table backends and paginators
  • Everything is an entry point; nothing is a fork

The test for whether we got this right: an analyst should never see the word “semaphore”, and a software engineer should never have to fork the repo to add a connector.

03 — Why this is a rebuild

Four findings from the current code

I read the engine before writing this. These are not style complaints — each one independently blocks something you explicitly asked for, and all four sit in code the TUI and the web studio both depend on.

Finding 1 · blocks operators, comparisons, dataframes

Every value is stringified on the way out of a step

The context declares string-only storage, the engine casts step output with str(), and the resolver casts again on every read. A JSON number that arrives as 42 is stored as "42"; a response body becomes a string the next step must re-parse.

app/core/models/context.py:24 workflow_variables: dict[str, str] app/core/engine/workflow.py:97 ctx.workflow_variables[step.output_variable] = str(step_result.output) app/core/engine/variable_resolver.py:57 return str(value) if value is not None else ...

Consequence: price > 100 becomes a string comparison, "9" > "100" is true, and there is nowhere to put a pandas DataFrame at all.

Replacement: a typed value store. Values keep their Python type end to end. Interpolation into a URL or header stringifies at the boundary only; expressions receive the real object.
Finding 2 · blocks “start the moment dependencies are ready”

The parallel engine schedules in barrier waves, not continuously

Its own docstring describes the loop: find the ready set, execute it concurrently, wait for all of it, then find the next ready set. Every wave is a barrier, so a one-second step waits for the slowest step beside it before its dependents can start.

app/core/engine/parallel_workflow.py:60-66 2. Find steps with no unmet dependencies (ready set) 3. Execute ready set concurrently 4. Mark completed steps, find new ready set
Replacement: a continuous ready-queue scheduler. A step is dispatched the instant its last dependency resolves, sharing one set of semaphores with everything else in flight. Section 10 shows the difference on a real graph.
Finding 3 · blocks “fast”

A new HTTP client, and a new TCP connection, per request

The executor opens httpx.AsyncClient inside an async with for every single call, then closes it. No keep-alive, no pooling, no HTTP/2, and a fresh TLS handshake on every request to the same host — the dominant cost in most API pipelines.

app/services/request_executor.py:33 async with httpx.AsyncClient(timeout=30.0) as client: response = await client.request(**kwargs) # client closed here
Replacement: one pooled client per host profile for the process lifetime, HTTP/2 on, keep-alive, configurable connection and per-host limits, exposed as workflow parameters.
Finding 4 · security

Secrets silently downgrade to base64

If cryptography is not installed, encrypt_secret() falls back to base64 and returns successfully. Base64 is an encoding, not encryption. The user is never told their credentials are stored in plain text, and the key file is written without restrictive permissions.

app/core/secrets.py:38-46 fernet = _get_fernet() # returns None on ImportError if fernet: ... # else: base64 fallback, no warning
Replacement: hard failure instead of silent downgrade, OS keyring first with an encrypted file fallback, 0600 on the key, and redaction applied at the reporter so secrets cannot reach a log, a bar label, or a trace dump.

The weight budget

The failure mode for a project like this is not running out of features — it is ending up with 40,000 lines nobody wants to touch, which is precisely how the current repository got three front ends. So the size target is a constraint with a number on it, checked in CI:

Four rules make the budget hold, and they are the ones worth arguing about in review:

  • No abstraction until the second caller. The current codebase has a contracts/ package of interfaces with exactly one implementation each. Interfaces earn their place when something actually varies — the reporter, the table backend, the paginator — and nowhere else.
  • Reuse before writing. Every dependency in the tree does three or four jobs: httpx for pooling, HTTP/2, and retries; typer for the whole CLI surface, help text, and shell completion; pydantic for validation and the JSON Schema that drives plugin help and the generated reference docs; aiosqlite for state, the cache index, and the bundled SQLite plugin; pyarrow for Parquet, spilling, and zero-copy process handoff. Five libraries total.
  • One deliberate exception: the terminal. The live region is written by hand rather than taken from a rendering library, and rich is dropped entirely. Section 13 argues the case — briefly, it is the most breakage-prone surface in the product, it must survive a worker pool writing underneath it, and it is the one thing we cannot debug in a user’s terminal. Two hundred and fifty lines we control beat a general-purpose renderer we do not.
  • One mechanism per concept. One registry pattern shared by functions, plugins, and paginators. One dispatch table for every operator. One event stream feeding every verbosity level. Where the current code has a service, a repository, and a contract per noun, the rewrite has one module.
  • Deleting counts as progress. If a milestone adds a feature and the total shrinks, that is the best possible outcome and it gets said out loud in the commit message.
The honest tension: sections 06 through 13 describe a lot of capability, and capability costs lines. The budget is what forces each one to be implemented as configuration over a library rather than as new machinery — pagination is five small strategy objects, not a subsystem; lanes are a dictionary lookup, not a framework.
05 — The workflow model

One IR, two surfaces

JSON and SCLPLL are two spellings of the same intermediate representation. The IR is canonical; both surfaces round-trip through it, and sclpl convert moves between them without loss. An analyst starts in JSON; a data engineer switches to SCLPLL when the JSON gets noisy; neither is second-class.

Step kinds

KindPurposeShape
httpOne request, optionally paginatedget/post/… + headers, query, body, paginate, retry
fnCall a built-in or plugin functionfn: name, with: {…}
letBind an expression to a namelet: {total: "sum(@rows.amount)"}
foreachFan out over a collection into the same graphover, as, body, max_parallel
ifConditional subgraphwhen, then, else
while / do_whileRepeat until a predicate flipswhile, body, max_iterations
gateAssert, or stop the branchassert, message, on_fail
parallelExplicit grouping for shared limitssteps, limit

Handoffs are explicit

The current engine mutates one shared dictionary, so any step can clobber any other and nothing is reproducible. In the new model a step declares what it reads (needs plus any @ref in its expressions) and what it produces (its id). The graph is derived from those references, which means the DAG is inferred, not hand-maintained — if you reference @orders, you depend on orders, and forgetting to list it is not a class of bug that exists.

Rules

Named, reusable predicate sets, so validation lives in one place instead of being copy-pasted into every step:

"rules": {
  "healthy":  "status == 200 and body.errors == null",
  "throttled": "status == 429 or status == 503"
},
"steps": [
  { "id": "fetch", "http": {...},
    "assert":   "healthy",       // fail the step if false
    "retry_if": "throttled",     // retry with backoff
    "skip_if":  "@feature.enabled == false" }
]
06 — Import, modes & invocation

Run a colleague’s pipeline by name, at the depth you need

A workflow should be something you install once and then invoke like any other command — not a path you have to remember. And a twenty-step pipeline should be runnable at three depths without maintaining three copies of it.

The invocation form

sclpl <workflow> [mode] [inputs…] [outputs…]

# by registered name, partial mode, one input, one output
sclpl orders partial customers.csv report.csv

# by file path, full mode, defaults for everything else
sclpl ./pipelines/orders.sclpll full

# named ports when positional order is not obvious
sclpl orders smoke --in customers=data/c.csv --out report=out/r.xlsx

# explicit form, for scripts and CI — always unambiguous
sclpl run orders --mode partial --in customers=c.csv --out report=r.csv

Resolution order for the first argument: a known subcommand wins; otherwise an existing file path; otherwise the project registry (.sclpl/workflows/); otherwise the user registry (~/.sclpl/workflows/). A miss prints the near-matches rather than a bare error. Scripts should use the explicit sclpl run form — it never has to guess.

Importing

sclpl import ./orders.sclpll                 # registers as "orders"
sclpl import ./p/ --recursive                # a whole directory
sclpl import https://ex.co/etl.json --as etl # from a URL, renamed
sclpl import ./orders.json --project         # into .sclpl/, committed with the repo

sclpl list                                   # names, versions, modes, ports
sclpl show orders                            # resolved definition + mode matrix
sclpl remove orders --version 2

Imports are content-hashed and versioned, so re-importing a changed file creates a new version rather than silently replacing one someone else depends on. sclpl run orders@3 pins a version. Import validates before registering — a workflow that would not run never enters the catalogue.

Modes select a subgraph

Modes are declared once, at the top of the workflow, so the answer to “what does partial actually run?” lives in one readable place instead of scattered across twenty step definitions:

"modes": {
  "smoke":   { "include": ["auth", "fetch_*"], "limit": { "max_pages": 1 },
               "vars": { "row_limit": 100 } },
  "partial": { "exclude": ["enrich_*", "geo_*", "report_pdf", "publish_*"] },
  "full":    { "all": true },
  "default": "partial"
}
smokeci gate 4 / 20
partialdaily 12 / 20
fullweekly 20 / 20
step runs in this mode pruned from the graph · sclpl show orders prints exactly this matrix

Selectors accept explicit ids, globs, and tags ("include": ["tag:cheap"]), and a mode may extend another so full is written as “partial plus these”. A mode can also override variables and limits — which is what makes smoke genuinely cheap rather than merely shorter.

Mode selection is a graph operation, not a filter. Pruning a step whose output a kept step still needs is a validation error, caught by sclpl validate --mode partial before a single request goes out. The error names the missing producer and offers the three legitimate ways to satisfy it: bind it to an input file, serve it --from-cache, or declare a stub value in the mode block.

Ports: how inputs and outputs bind

Positional file arguments are only unambiguous if the workflow says what it expects, so ports are declared:

"inputs":  [ { "name": "customers", "format": "csv",  "required": true },
             { "name": "overrides", "format": "json", "required": false } ],
"outputs": [ { "name": "report",    "format": "csv" } ]
  • Positional arguments bind in declaration order — inputs first, then outputs. Mismatched counts produce an error listing the ports, not a stack trace.
  • --in name=path and --out name=path bind by name and win over positional.
  • Format is inferred from the extension and overridable with --in customers=data.txt:csv.
  • - means stdin or stdout, so sclpl orders partial - - is a filter in a pipe.
  • A glob binds a port to a list of files, which feeds a foreach naturally.
  • A port unbound in a given mode is simply absent from the pruned graph — that is often the point of the mode.
07 — Expressions & operators

Every operator is a generalized function

You asked for operators to be generalized functions. That is exactly the design: there is one dispatch table, and infix syntax is sugar that compiles to a call in it. a.total > 500 and gt(a.total, 500) produce the same IR node.

Dispatch is on the runtime type of the first argument, so one name works across scalars, lists, and tables. sort on a list sorts a list; sort on a DataFrame becomes sort_values; sort on a Dask frame stays lazy. A plugin registers a new type by registering overloads — it never patches the parser.

@overload("filter", Table)
async def _(t: Table, where: Expr, *, engine) -> Table:
    return engine.filter(t, where)

@overload("filter", list)
async def _(xs: list, where: Expr) -> list:
    return [x for x in xs if await where.eval(row=x)]

Path access

Dot and bracket notation with wildcards, over anything addressable — response bodies, headers, prior step output, environment, loop variables:

@orders.body.data[0].customer.email      single value
@orders.body.data[*].id                  projection → list
@orders.body.data[?(total > 500)].id     filtered projection
@orders.headers["x-request-id"]          bracket for odd keys
@orders.status                           status code, typed int
{{base}}/orders/{{order.id}}             interpolation, stringified at the edge
A missing path is an error, not a silent pass-through. The current resolver returns the literal text {{a.b.c}} when a lookup fails, so a typo becomes a request to a URL containing braces. The new resolver fails the step with the path, the value that was actually there, and the nearest valid key.

The contract for a custom function

Typed signature, no magic context dictionary, async-aware, and versioned — the version participates in the cache key so bumping it invalidates exactly the affected entries and nothing else.

from sclpl import function, Table

@function(name="top_customers", version=2)
async def top_customers(orders: Table, *, n: int = 10, by: str = "total") -> Table:
    """Return the n highest-spending customers. Shown by `sclpl fn describe`."""
    return orders.group_by("customer_id").agg({by: "sum"}).sort_by(by, desc=True).take(n)

Type hints are not decoration: they generate the JSON Schema for validation, the --help text, the shell completion, and the coercion rules that let a tier-1 user pass "10" from a JSON file into an int parameter.

09 — Plugins

Connectors without forking

Plugins are ordinary installable Python distributions found through importlib.metadata entry points, plus a local plugins/ directory for work in progress. A plugin may contribute six kinds of thing, and each becomes usable from JSON, SCLPLL, and the CLI at the same moment:

# sclpl_postgres/plugin.toml
[plugin]
name = "postgres"
version = "1.2.0"
api = "sclpl/1"              # engine ABI it was built against
capabilities = ["network", "secrets:read"]   # declared, prompted, recorded

[[connector]]
name   = "postgres.query"
schema = "schemas/query.json"   # JSON Schema → validation, --help, completion
lane   = "thread"               # optional; the engine infers this otherwise

Three properties make this maintainable rather than a plugin zoo:

  • Declared capabilities. A plugin states whether it touches the network, the filesystem, secrets, or subprocesses. sclpl plugin list shows them and --deny-capability enforces them. A scraper plugin cannot quietly read your secrets.
  • Schema-first configuration. The JSON Schema is the single source for runtime validation, generated help, and editor completion, so a tier-1 user gets a precise error at sclpl validate time rather than a stack trace at hour two of a run.
  • A pinned ABI. api = "sclpl/1" lets the runtime refuse a plugin built for an incompatible engine instead of failing deep inside a run.

sclpl plugin scaffold my-thing generates a working, tested, typed plugin with one connector and one function, so tier 3 starts from something that already passes CI.

What ships in the box

Three bundled plugins, chosen because they cover the overwhelming majority of “get data in, get data out” without adding a single dependency. Everything else — Postgres, DuckDB, S3, scrapers — lives outside the wheel and installs on demand.

SQLite works out of the box because aiosqlite is already carrying the engine’s own state and cache index — the plugin is a thin connector over a driver that is loaded anyway, which is exactly the kind of reuse the weight budget is asking for. It is a real plugin using only the public plugin API, so it doubles as the proof that the API is sufficient:

# using it — tier 1, no Python involved
{ "id": "customers", "use": "sqlite.query",
  "with": { "db": "warehouse.db",
            "sql": "select id, name, region from customers where active = :active",
            "params": { "active": 1 } } }

{ "id": "save", "needs": ["joined"], "use": "sqlite.write",
  "with": { "db": "warehouse.db", "table": "orders_enriched",
            "mode": "replace", "rows": "@joined" } }
# implementing it — the whole read side of the plugin
@connector("sqlite.query", lane="thread", capabilities=["fs:read"])
async def query(db: Path, sql: str, params: dict | None = None) -> Table:
    """Run a SELECT and return the rows as a table."""
    async with aiosqlite.connect(db) as con:
        con.row_factory = aiosqlite.Row
        async with con.execute(sql, params or {}) as cur:
            return to_table([dict(r) async for r in cur])

Note what is absent: no connection-string parser, no dialect layer, no query builder. The parameter names become the JSON Schema, the Table return type puts it straight into the operator dispatch, and the declared lane tells the scheduler to keep the blocking driver off the event loop. That is the shape every plugin should have.

10 — Scheduling & concurrency

Dependencies pull work forward

This is the core of what you described: if a step’s dependencies are available it should start immediately, sharing whatever limits are free. Below is the same seven-step graph under both schedulers. The current wave scheduler idles workers at every barrier; the ready-queue scheduler finishes in the length of the critical path, which is the theoretical floor.

Wave scheduler today · 7 units

A1 B3 C1 D ← A2 E ← B1 F ← C3 G ← DEF1
0123456

Ready-queue scheduler new · 5 units

A1 B3 C1 D ← A2 E ← B1 F ← C3 G ← DEF1
0123456
step executing critical path (B→E→G = 5) worker idle at a barrier

How it works

  • Ready queue, not waves. Each node carries an unmet-dependency count. On completion the scheduler decrements its dependents and pushes any that hit zero — immediately, mid-flight.
  • Critical-path priority. The queue is a heap ordered by longest remaining path, so the step that gates the most downstream work starts first when capacity is scarce. That is the difference between 5 units and 6 on the graph above.
  • Layered semaphores. Global → per-host → per-tag, acquired in a fixed global order so the arrangement cannot deadlock. Fan-out from foreach injects nodes into the same graph, so a thousand-item loop shares the same limits instead of spawning a thousand unbounded tasks.
  • Adaptive concurrency. An AIMD controller per host raises concurrency while latency is flat and backs off on 429/503 or a rising p95 — honouring Retry-After exactly. Static caps remain available for the analyst who just wants --concurrency 4.
  • Cancellation is structured. asyncio.TaskGroup throughout; first Ctrl-C drains in-flight work and writes partial results, second aborts. --keep-going continues independent branches after a failure.

Lanes: threads and processes chosen for you

You asked that speed, handoff, and threads or processes be handled automatically. The planner classifies every step and assigns it a lane; nothing in the workflow file mentions a thread. A step’s lane is visible in sclpl explain and overridable with "lane": …, but the default should be right often enough that nobody bothers.

async

HTTP, sockets, file reads. Runs on the event loop. Thousands concurrent, bounded only by the semaphores.

thread

Blocking sync code — a plugin using requests or a DB driver. Offloaded to a thread pool so it cannot stall the loop.

process

CPU-bound work — large joins, parsing, compression. A process pool sized to the core count sidesteps the GIL.

serial

Memory-heavy steps. Admitted one at a time under memory pressure, with spilling preferred over eviction.

Classification uses three signals, in order: an explicit lane in the step or plugin manifest; the function’s own signature (an async def is async, a plain def touching a Table is a process candidate); and measured statistics from previous runs of the same workflow, kept in run history — so a step that has consistently burned four seconds of CPU is scheduled to the process pool the next time without anyone configuring it.

Workers

One worker abstraction serves all four lanes, which is what keeps this a few hundred lines rather than a framework. A worker is a loop that pulls the next ready node, acquires its semaphores, dispatches it to its lane, publishes the result, and wakes the dependents. The lane decides only where the call happens — on the loop, in run_in_executor against the thread pool, or in the process pool — never how the work is tracked.

  • Async workers scale with the concurrency limit, not the core count; they are cheap tasks, so --concurrency 200 is reasonable for a slow API.
  • The thread pool defaults to 32 and exists to quarantine blocking code. A badly behaved plugin stalls its own thread and nothing else.
  • The process pool is created lazily on the first process-lane step and sized to the core count, so a pipeline that never needs it never pays the fork cost.
  • Every worker is cancellable and every pool is drained in a finally, which is what makes Ctrl-C leave no orphans and no half-written output files.
  • Back-pressure is shared. Because all lanes admit through the same semaphore stack, the resource governor can slow the entire run by lowering one number.

Handoff across a lane boundary

Moving a value between the loop and a process is where naive engines lose all their speed to pickling. The engine picks the cheapest transfer available for the value it actually holds:

11 — Memory & caching

Memory should never be the reason a run dies

Four mechanisms, in the order they engage.

1 · Liveness analysis — automatic disposal

You asked for values to be discarded once nothing downstream needs them. Because the DAG is known at compile time — after mode pruning, so a partial run frees more, sooner — the planner computes the last consumer of every value and attaches a release point to it. When a step finishes, the store decrements a reference count on each of its inputs; at zero the value is freed and any spill file is deleted. Values marked keep, or bound to an output port, are pinned.

Honest limitation: inside while and foreach bodies, liveness must be conservative — a value referenced anywhere in a loop body stays live until the loop exits. sclpl explain --memory prints the computed release points so this is inspectable rather than mysterious, and --keep-all disables disposal for debugging.

2 · Spill to disk

Values above a threshold (default 64 MB) are written to the run’s scratch directory — Parquet for tables, pickle for arbitrary objects — and replaced in memory by a ValueRef that rehydrates on access. Steps never know the difference, and as section 10 notes, a spilled value crosses a process boundary for free. Scratch is cleaned on exit and reclaimable with sclpl cache prune.

3 · Resource governor

A sampler watches process RSS, system available memory, and open file descriptors. At the soft watermark (70% of budget) it stops admitting new steps and prefers spilling; at the hard watermark (85%) it reduces concurrency and warns in the status line with the actual numbers. The budget defaults to a share of system memory and is settable with --memory-budget 4G. The goal is that a run degrades to slower rather than dying.

4 · Content-addressed cache

Heavy caching that cannot serve a wrong answer, because the key is derived from everything that could change the result:

key = sha256(
    step_kind, method, resolved_url, sorted_query, body_digest,
    headers_minus_volatile, function_name, function_version,
    input_value_digests, plugin_version, engine_version,
    credential_identity_salt        # hash of the credential, never the credential
)

The key deliberately excludes the mode, so a partial run and a later full run share every step they have in common — which is what makes “run partial all day, full once at night” cheap.

13 — The view

An apt-grade live region

You were specific about this, so here is the mechanism rather than a promise. apt keeps its bar pinned while log lines scroll above it by setting the terminal’s scroll region with DECSTBM — ESC[1;{rows-k}r — reserving the bottom k lines. Ordinary output scrolls inside the region above; the reserved lines are repainted in place with cursor-save and cursor-restore.

We write those bytes ourselves rather than taking Rich. This is the one place the reuse rule in section 04 is deliberately overridden, and the reason is that a pinned live region is the single most breakable thing in the product: a general-purpose renderer that assumes one writer will tear frames the moment a worker pool writes underneath it, and when it breaks it breaks in someone else’s terminal where we cannot debug it. Owning the escape sequences costs about 250 lines and buys byte-exact snapshot tests, one failure model, and no dependency in the hot path.

What “break-proof” actually means here

  • One writer, always. Exactly one task owns the handle to stderr; every worker, plugin, and log record arrives as an event on a queue. Nothing else may write. This alone removes the entire class of interleaved and torn output that makes live regions look unreliable.
  • Probe once at startup, never re-probe. isatty, TERM, COLORTERM, NO_COLOR, CI, and on Windows an explicit ENABLE_VIRTUAL_TERMINAL_PROCESSING call — if enabling VT fails, we are in plain mode for the whole run. The renderer never changes its mind halfway through.
  • A ladder that only goes down. full (scroll region, colour, Unicode) → simple (repaint the last k lines with carriage return and erase-line, no scroll region) → plain (one line per event, no cursor movement). Any write error, unsupported sequence, or encoding failure drops a rung permanently. It never climbs back up.
  • Nothing ever wraps. Every line is measured and truncated to the terminal width before it is written, because a wrapped line inside a pinned region is what corrupts the display. Width comes from os.get_terminal_size with an 80×24 fallback, re-measured on SIGWINCH.
  • Glyphs are probed, not assumed. The spinner and box characters are encoded against the stream encoding at startup; on failure the renderer swaps to an ASCII set. Windows code pages are the usual culprit and the usual source of mojibake.
  • Restoration is guaranteed three ways. Reset of the scroll region and cursor happens in a finally, in an atexit hook, and in the SIGINT/SIGTERM handlers. The reset is idempotent, so running all three is harmless — and the terminal is never left broken, which is the failure users actually remember.
  • Bounded repaint. Frames are coalesced and capped at 10 Hz regardless of event volume, so a fast pipeline cannot flood a slow terminal, and output over SSH stays usable.
  • Subprocesses are quarantined. Child processes inherit SCLPL_RENDER=plain and their output is captured and re-emitted through the same queue, so a plugin shelling out cannot write into the region.
  • Escape hatches that always work. --plain forces the bottom rung; SCLPL_RENDER=plain|simple|full pins a level for an environment we guessed wrong about. Neither requires a code change to unblock someone.

The test harness runs the renderer against a real pty and asserts the emitted byte sequence against golden snapshots at each rung, plus a fuzz test that resizes and interrupts mid-run and asserts the terminal state is fully restored. If a terminal is not on that list, the ladder puts it on plain lines rather than guessing — a boring, correct fallback is the whole point.

Six rules keep this a convenience rather than a second interface — which is the trap that produced the TUI we are deleting:

  • It always prints the command it is about to run, then asks. The launcher is a way to learn the CLI, not an alternative to it — after a week you type the command directly, which is the intended outcome.
  • Only when both stdin and stderr are a terminal. Piped, redirected, or in CI, bare sclpl prints help and exits 2. It can never hang a script waiting on input.
  • Plain prompts only — line-based reads and ordinary writes, no cursor addressing. The launcher sits below the render ladder in section 13, so it cannot be broken by a terminal the live region would struggle with.
  • Numbers, plus q to quit and ? for help, at every level. Every submenu has the same shape, so there is one interaction to learn. Ctrl-C backs out one level; twice exits.
  • Defaults in brackets, Enter accepts. The mode shown is the workflow’s declared default; ports are pre-filled from the last run of that workflow.
  • Nothing destructive without naming the target. Overwriting an existing output, removing a workflow, or clearing history requires an explicit confirmation that says what will be lost.

Budgeted at ~250 lines, because it is a loop over a list of commands the CLI already exposes — it holds no state and duplicates no logic.

18 — Risks

Where this could go wrong

Expression language scope creep

The operator list in section 07 is already large, and every real pipeline will want one more function. Mitigation: the dispatch table is the extension point — new operators arrive as plugin overloads, and the core list is frozen after M6 unless something cannot be expressed at all.

Modes becoming a second, shadow workflow language

Include/exclude selectors with globs, tags, inheritance, variable overrides and stubs can quietly grow into a configuration language of its own. Mitigation: modes may only subtract steps and override scalars — they can never add a step, change a dependency, or alter an expression. If a mode needs to do more than that, it is a separate workflow.

pandas is a heavy dependency for a tier-1 install

pandas plus pyarrow is roughly 100 MB, which is a lot for someone who only wants to hit two endpoints. Mitigation: core install stays light; pip install sclpl[data] adds the table stack, and any function that needs it raises a precise install instruction rather than an ImportError. See the open decision below.

We now own every terminal bug

Dropping Rich means Windows Terminal, ConHost, tmux, mosh, VS Code’s terminal, and every CI runner become our problem rather than a maintainer’s. That is a real cost and it is accepted deliberately, because the alternative is a breakage we can neither reproduce nor fix. Mitigation: single-writer discipline removes the common cause outright; the fallback ladder only descends, so an unrecognised terminal gets boring plain lines instead of a guess; a pty harness asserts golden byte sequences at each rung; a fuzz test resizes and interrupts mid-run and asserts full restoration; and --plain plus SCLPL_RENDER unblock any user without a release.

Liveness analysis freeing something still in use

A wrong disposal is a crash mid-run — the worst failure mode here. Mitigation: conservative by construction (dynamic scopes pin their values), disposal is off under --keep-all, and a debug mode tombstones freed values so any access raises a precise error naming the step instead of a KeyError.

Automatic lane assignment guessing wrong

Sending a cheap step to a process pool costs more in transfer than it saves, and history-based tuning can lock in a bad early sample. Mitigation: a size threshold below which the process lane is never chosen, statistics kept as a rolling median rather than a single observation, sclpl explain showing every assignment, and an explicit lane override that always wins.

Ships as sclpl. No sclplapi alias — nothing depends on it yet, and one name is one thing to document.
✓ 2 · Bare shorthand
sclpl orders partial in.csv out.csv is supported, with explicit sclpl run always available and required in scripts and CI. Resolution order is deterministic: subcommand → file path → project registry → user registry.
✓ 3 · pandas is an extra
pip install sclpl[data]. The missing extra is reported by preflight — at validation, and at the start of every run — never mid-pipeline after twenty minutes of work. See the preflight block in section 14.
✓ 4 · SCLPLL v2, no compatibility
Clean break, and no v1 converter is built. The project is pre-release; the four example workflows are rewritten by hand. This deletes a migration path we would otherwise have to test forever.
✓ 5 · Run history
SQLite, retention configurable, default 5 runs. Each run is dated, named, and taggable, and the whole history is searchable. Full model in section 14.
✓ 6 · Deletion
Delete outright in M0. The baseline commit 1b1abe0 is the archive; no dead code rides along beside the rewrite.
Project history: the full pre-rework state is preserved as commit 1b1abe0. The implementation plan and specification are committed under docs/cli-rebuild/; the current release status is maintained in the vault and public documentation. The TUI, FastAPI layer, and SPA were removed in M0.
